Overview

로컬 개발 환경을 하나의 모델로 운영합니다.

Workbench는 프로젝트, Git worktree, 코딩 Agent task, terminal backend, 환경 진단을 연결하는 headless control plane입니다. CLI가 상태와 안전 경계를 소유하고 Dashboard, LazyVim, cmux 같은 client는 같은 계약을 사용합니다.

5분 안에 시작하기구조 이해하기Dashboard 열기
Explicit runtimeCLI 또는 사용자가 시작한 loopback Dashboard server
Local firstregistry와 설정은 사용자 XDG 경로에 저장
Typed actions브라우저에서 임의 shell command를 실행하지 않음
Cross-platformmacOS, Linux/WSL, native Windows backend 계약
현재 범위

이 문서는 현재 구현된 기능만 설명합니다. 독립 Desktop 앱과 외부 Vault는 제공하지 않으며, tmux session ownership은 tmux user option으로 관리합니다.

Get started

빠른 시작

설치부터 첫 프로젝트를 Dashboard에서 확인하기까지의 최소 흐름입니다.

  1. 1

    빌드하고 설치합니다.

    cd workbench
    make test
    make install

    기본 설치 위치는 ~/.local/bin/wb입니다.

  2. 2

    환경 계약을 확인합니다.

    wb config validate
    wb doctor

    기본 Doctor는 core 실패에만 non-zero를 반환합니다. 모든 optional provider까지 요구하려면 --strict를 사용합니다.

  3. 3

    프로젝트를 등록합니다.

    wb projects add ~/home/projects/example --id example
    wb projects list --json

    경로는 canonical absolute path로 저장되고 ID는 장비 간 portable identity가 됩니다.

  4. 4

    프로젝트를 엽니다.

    wb open example
    wb open example --backend tmux

    auto는 현재 tmux, profile priority, platform fallback 순서로 선택합니다.

  5. 5

    Dashboard를 시작합니다.

    wb dashboard
    wb dashboard --open none --port 0
    wb server start --open browser

    Dashboard는 127.0.0.1에만 bind합니다. Foreground는 Ctrl-C, background는 wb server stop으로 종료합니다.

Concepts

현재 아키텍처

Workbench core가 canonical state와 정책을 소유합니다. Client는 표시와 입력을 담당하고 backend/provider는 검증된 요청만 실행합니다.

ClientsCLIDashboardLazyVimcmux actions
→
Control planeProjectsWorktreesAgent registryDoctor
→
Executioncmuxtmux / shellWindows TerminalGit / binbox

요청 흐름

  1. Client가 project ID, task ID, backend 같은 typed input을 전달합니다.
  2. Core가 config와 registry를 읽고 ID, ownership, platform capability를 검증합니다.
  3. 선택된 adapter가 argument array로 외부 프로그램을 실행합니다.
  4. 결과와 recovery가 CLI envelope 또는 Dashboard snapshot으로 돌아옵니다.
Source of truth

cmux, LazyVim, Dashboard는 별도 project/task registry를 만들지 않습니다. Workbench가 unavailable일 때만 문서화된 compatibility fallback을 사용합니다.

Concepts

Projects와 Profiles

Project는 portable ID와 장비별 canonical path를 연결합니다. Profile은 backend 우선순위와 editor, Windows Terminal 정책을 묶습니다.

Project lifecycle

wb projects add /absolute/path --id alpha
wb projects show alpha --json
wb projects list
wb projects remove alpha

remove는 registry entry만 삭제합니다.

Profile example

schema_version = 1
default_backend = "auto"
prefer_current_tmux = true
backend_priority = ["cmux", "tmux", "shell"]

Sessionizer migration

wb migrate sessionizer --check
wb migrate sessionizer --apply

항상 --check로 diff를 먼저 검토합니다.

auto 순서

  1. 명시한 --backend가 있으면 그것을 검증합니다.
  2. Project와 active profile default를 확인합니다.
  3. prefer_current_tmux=true이면 현재 tmux를 우선합니다.
  4. backend_priority와 platform fallback을 적용합니다.
Guides

Worktree 운영

Git porcelain이 실제 checkout의 권위이며 registry는 wb가 만든 worktree의 stable ID와 ownership만 기록합니다.

wb worktrees create alpha feature/api --base main
wb worktrees list alpha --json
wb worktrees remove wt-alpha-feature-api-1a2b3c4d
wb worktrees remove wt-alpha-feature-api-1a2b3c4d --delete-branch
Create다른 worktree에서 checkout한 branch는 거부합니다.
Removemanaged identity, path, branch를 다시 확인하고 dirty/locked 상태를 거부합니다.
Branch기본은 보존이며 삭제는 exact confirmation과 safe git branch -d를 사용합니다.
Guides

Agent tasks와 ownership

Workbench task는 Codex/Claude lifecycle과 backend reference를 registry에 기록합니다. 비슷해 보이는 process를 PID나 화면 문자열로 추측해 제어하지 않습니다.

wb agents start alpha --agent codex --backend tmux
wb agents list --project alpha --json
wb agents show task-19c...
wb agents jump task-19c...
wb agents stop task-19c...
State의미동작

waiting사용자 입력 필요task로 jump
idle활성 상태지만 현재 작업 없음jump/stop capability 확인

Legacy scrape

state_source=scrape는 compatibility observation이며 Workbench stop authority가 없습니다.

Guides

Dashboard 사용법

Dashboard는 canonical state를 새로 만들지 않는 thin client입니다. snapshot은 15초마다 그리고 Refresh 후 다시 읽습니다.

Projects

등록 프로젝트와 active Agent 수를 보여주고 선택 context를 바꿉니다.

Project actions

Open, Start Codex, Start Claude typed action을 제공합니다.

Scheduler

background server job의 성공/실패, 다음 실행, Environment 만료 집계를 표시합니다.

Metrics

active Agents, worktrees, Git changes와 branch를 요약합니다.

Context

선택 project의 environment 연결, 만료 상태, AWS/Kubernetes metadata, export key 이름, secret reference 상태만 읽기 전용으로 표시합니다. 값과 raw reference는 표시하지 않습니다.

Panels

Active Agents와 접힌 Task history, worktrees, changed files, Doctor를 표시합니다.

Task detail

active task만 jump/stop을 제공하며 terminal task action은 비활성입니다.

Theme

System, Light, Dark 선택은 브라우저 localStorage에만 저장됩니다.

Operations

Doctor, 관측, 복구

wb doctor
wb doctor --json
wb doctor --profile personal --strict
available

검사가 통과했거나 provider/backend를 사용할 수 있습니다.

unavailable

적용되는 capability가 실패했습니다. recovery를 확인합니다.

skipped

플랫폼에 적용되지 않거나 아직 관찰되지 않았습니다.

Scope

  • core: config/state schema, Git, shell처럼 핵심 workflow에 필요합니다.
  • optional: tmux, cmux, Neovim, Agent CLI처럼 일부 workflow에 필요합니다.
  • disabled: 현재 플랫폼에 적용되지 않으며 strict 실패를 만들지 않습니다.

Compatibility readiness

compatibility:nvim-projects와 compatibility:agents는 가장 최근에 관찰한 source를 보여줍니다. 최신 fallback은 optional unavailable입니다.

자동 삭제 금지

timestamp는 advisory evidence입니다. clock rollback, 다른 장비, 미실행 workflow가 있으므로 fallback 제거 권한이 아닙니다.

Dashboard와 Guide는 restrictive CSP, frame denial, no-referrer, no-sniff, no-store를 사용합니다. Theme preference만 device-local localStorage에 저장됩니다.

Atomic state

Agent 기록은 Unix/WSL의 ${XDG_STATE_HOME:-~/.local/state}/workbench/agents.json 또는 Windows의 %LOCALAPPDATA%\workbench\agents.json에 저장됩니다. Dashboard Task history는 현재 해석된 전체 경로를 표시합니다. Registry write는 mode 0600 same-directory temporary file, flush, rename을 사용하며 history clear 전에는 backups/에 이전 파일을 보존합니다. compatibility observation은 bounded per-tuple state라 timestamp backup을 만들지 않습니다.

Operations

문제 해결

01wb를 찾을 수 없습니다.

make install 후 ~/.local/bin이 PATH에 있는지 확인합니다.

02wb open이 예상하지 않은 terminal을 선택합니다.

wb doctor, prefer_current_tmux, backend_priority를 확인하고 --backend로 selection 문제를 분리합니다.

03Worktree를 제거할 수 없습니다.

git status와 managed/dirty/locked 여부를 확인합니다. Workbench는 --force를 사용하지 않습니다.

04Agent jump/stop이 거부됩니다.

wb agents show로 backend reference와 state source를 확인합니다. safely reconnectable하지 않으면 추측 제어를 하지 않습니다.

05Dashboard action이 403입니다.

같은 URL과 origin을 사용하고 오래된 tab은 새로고침합니다. token은 process마다 새로 생성됩니다.

06Doctor strict만 실패합니다.

optional unavailable을 확인하고 이 장비에서 해당 workflow가 필수인지 판단합니다.

07Fallback 제거 시점을 모르겠습니다.

대표 사용 주기, 다른 장비, clean profile, rollback을 함께 검토합니다. point-in-time available만으로 삭제하지 않습니다.
